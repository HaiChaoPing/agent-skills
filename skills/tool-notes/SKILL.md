# tool-notes

## 何时使用

用户要一份具体工具的"学习笔记/使用笔记/速查/上手文档"，且希望以后能反复查阅时使用。

不适用：纯原理教材、API 参考手册、项目 README（后者用 md-docs）、只要一条命令的即时问答。

## 交互协议

**第一轮（一条消息，≤6 问）**：工具与版本/运行环境；想用它完成什么任务；已有基础；必须覆盖与不关心的侧面；笔记放哪、单文件还是目录。允许用户回答"不知道"。

**调研**：官方文档、quickstart、安装方式、主要替代、常见坑；确认版本。文档能回答的问题不要反问用户。

**第二轮（提纲镜像，必须等用户确认）**：调研后给出提纲：按用户列的每个侧面各设一节，**顺序与用户列举顺序一致**；逐条标注该侧面"独立成节/需与相邻合并/缺前置条件"。请用户确认或调整顺序。不重组场景，不替用户挑选主线。

用户只给零散功能点时，就按功能点成节，每节写清"解决什么问题、什么时候用"，不强行串成故事。

**第三轮（交付确认）**：文件名与是否拆分、深度（quickstart/平衡/参考）、是否附 `quickstart/` 目录。

## 笔记契约

**结构**

1. 文首放目录（链接列表），目录即提纲：`# <工具名>` → `## 速查` → `## 安装与入口` → `## 主用法`（按主题分章） → `## 排障` → `# 开发者内容` → `## 原理` → `## 扩展点`。
2. 所有使用内容必须在 `# 开发者内容` 之前，不得回插。
3. 每个 `##` 章开头写一句"这一章解决什么问题"，再进命令。
4. `## 速查` 给 5–15 行最高频命令，每行一条注释。

**内容**

- 开头 1–3 句定位：是什么、解决什么问题、与主要替代的关系；随后官方链接、安装/入口命令、最强特性、何时不该用。
- 一个场景一份笔记；默认一工具一份；用户侧面 >3 个或预计 >400 行时，按侧面拆分并写 `index.md`。
- 每节给最小可运行示例；shell/config 块内注释解释参数；给预期输出或可观察结果；标版本差异。
- 原理、内部机制、扩展点一律放最后"开发者内容"，只解释排障必需的部分。
- 语言中文、术语保留英文；注释 ≤1 行；不写营销话术。

**准确性（五条硬规则）**

1. 官方链接 ≥2，分别覆盖安装入口与主要行为；每个大节的关键结论至少 1 个可溯源链接。
2. 只有本次运行验证过的输出才能标"实测/已验证"。官方文档与 `--help` 的描述句只能当"文档说明"，不得写成运行时行为。
3. 跨节引用必须闭合：文中调用的 recipe、文件、变量、服务，必须在同一篇里定义，或给出获取方式。
4. 复杂工具（有引擎、模板、外部文件、服务）默认附 `quickstart/`；用户拒绝目录时，改为内嵌一份完整可运行配置，并声明"单文件替代 quickstart/"。
5. 边界：写"何时不该用"，至少给 1 个替代与一句话取舍，不展开成评测。

**禁止**

原理教材；参数说明放代码块外；原理与操作混排；图片/PDF/附件；为大工具写无边界长文；编造 flag/默认值；无取舍的功能清单。

## 自检

交付前逐条确认：

- 范围已确认，用户每个侧面都映射到章节或标为"范围外"。
- 生命周期完整：准备、主路径、验证、清理都有落点（省略的写明原因）。
- 每条命令可直接执行；重要参数在块内注释；关键步骤有预期输出。
- 每条"实测"都能指到本次运行的输出；未验证项标"待核实"。
- 跨节引用的 recipe/文件/变量都有定义；示例配置能一次跑通。
- 官方链接 ≥2；边界含替代与取舍。
- 原理全部后置；无图片/PDF/附件。
- >400 行已拆分并写 `index.md`。

## 不确定处理

- 未验证的命令、默认值、版本行为：标"待核实"，写明已查来源（官方文档章节或 `--help`）。
- 文档描述与实测不一致时，以实测为准，并把两者差异写出来。
- 官方文档缺失或自相矛盾：写明冲突并给保守做法。
- 不把推测写成事实，不编造 flag。
